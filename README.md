# Лаборатори 3 — Чанарын сценарио, SLO, k6 threshold

**Оюутан:** Ган-Оргил  
**Оюутны код:** B232270091  
**Хичээл:** F.CSA313 — Программ хангамжийн чанарын баталгаа ба тест

Туршсан орчин: Windows x64, Node.js `v24.22.1`. `k6 version` командын гаралт:

```text
k6.exe v1.8.3 (commit/58bbfd8e48, go1.26.11, windows/amd64)
```

Командын эх гаралт: [results/environment.txt](results/environment.txt).

Энэ ажлаар локал API-ийн чанарын шаардлагыг хэмжиж болох сценарио болгон бичиж, SLO болон k6 threshold руу шилжүүлж шалгав. API нь сагсанд нэмэх, тайлан авах, төлбөр хийх гэсэн гурван үйлдэлтэй. Төлбөрийн хүсэлтийн ойролцоогоор 5% нь зориуд 500 алдаа буцаана. Тайлангийн хариуг 200–400 мс саатуулна.

## Чанарын сценарио

| Орчны төлөв | Нэг машин дээр 20 VU тогтмол ажиллана. VU бүр гурван хүсэлтээ дарааллаар явуулаад 1 секунд хүлээнэ. Тайлангийн хүлээлттэй нийлээд ойролцоогоор 45–47 хүсэлт/с үүснэ; `/cart/add` нь ойролцоогоор 15 хүсэлт/с. |
| Гадаад өдөөлт | Хэрэглэгч `POST /cart/add` хүсэлт явуулах. |

Сценарио бүрд хэрэглэгчийн үйлдэл эсвэл серверийн эвдрэл, ачаалал, ажиглах хариу, тоон хэмжүүрээ тусад нь бичсэн. Ингэснээр шаардлага нь итгэмжтэй, хэрэглэгчид үнэ цэнэтэй, тодорхой, нарийн, ойлгомжтой гэсэн таван шинжийг хангаж байгаа эсэхийг шалгаж болно.

## SLO болон threshold

| Сценарио | SLI | Босго | Цонх, нөхцөл | k6 threshold |
| --- | --- | --- | --- | --- |
| Performance | `/cart/add` хариу хугацаа | p95 < 20 мс | 20 VU, 1 минут; chaos үед мөн шалгана | `http_req_duration{name:cart}: p(95)<20` |
| Reliability | `/pay` алдааны хувь | < 8% | 20 VU, 1 минут; chaos үед мөн шалгана | `http_req_failed{name:pay}: rate<0.08` |
| Availability | Бүх хүсэлтийн амжилтын хувь | ≥ 90% | Хэвийн үед 1 минут, chaos үед 2 минут, 10 секундийн зогсолттой | `checks: rate>=0.90` |
| Availability | VU-д ажиглагдсан сэргэх хугацаа | p95 < 12 секунд | Chaos туршилт; анхны бүтэлгүй `/cart/add`-аас дараагийн амжилттай хүсэлт хүртэл | `recovery_ms: p(95)<12000` |
| Тайлангийн performance | `/report` хариу хугацаа | p95 < 450 мс | 20 VU, 1 минут; chaos үед мөн шалгана | `http_req_duration{name:report}: p(95)<450` |

Сагсанд нэмэх үйлдэл нь диск, өгөгдлийн сан ашиглахгүй тул localhost дээр 200 мс гэдэг сул хязгаарын оронд 20 мс сонгов. Төлбөрт 5%-ийн санамсаргүй алдаа суулгасан учраас богино туршилтын хэлбэлзлийг тооцож 8%-ийн босго авлаа. Availability-д 90% сонгосноор 2 минутын цонхонд 10 секунд зогсох тохиолдлыг эхлээд цагаар тооцож харьцуулна. Сэргэх хугацаанд 10 секундийн зогсолт дээр дахин асах болон VU дараагийн хүсэлтээ явуулах хугацааг нэмж 12 секундийн хязгаар тавив. Тайлангийн 450 мс босго нь кодын 200–400 мс хүлээлт дээр хүсэлт боловсруулах багахан хугацааг тооцсон сонголт.

Цагаар тооцсон error budget: `120 × (1 − 0.90) = 12 секунд`. Энэ нь тасралтгүй хугацаагаар хэмжсэн хүртээмжийн тооцоо. Харин `checks` хүсэлтийн амжилтыг хэмждэг тул энэ 12 секундийг хүсэлтийн 10%-тай шууд адилтгаж болохгүй. Мөн `/pay`-ийн зориудын алдаа сервер хэвийн ажиллаж байх үед ч хүсэлтийн budget-ээс зарцуулна.

## Ажиллуулах

Node.js, npm, k6 суусан орчинд:

```sh
npm ci
node scripts/run-tests.js pass
node scripts/run-tests.js fail
node scripts/run-tests.js chaos
```

Ажиллуулагч серверийг өөрөө асааж, тестийн дараа зогсооно. Тиймээс энэ аргаар ажиллуулахын өмнө 3000 портыг чөлөөлнө. Chaos хувилбар 2 минут үргэлжилж, тест эхэлснээс 30 секундийн дараа зөвхөн өөрийн асаасан серверийн процессыг зогсоогоод 10 секунд хүлээж дахин асаана. Бүх k6 гаралт болон exit code `results/` дотор хадгалагдана. `fail` болон SLO зөрчсөн `chaos` команд тэгээс ялгаатай exit code буцаах нь туршилтын хүлээгдсэн үр дүн.

Серверийг тусдаа терминалд `npm start` командаар ажиллуулсан бол k6 скриптүүдийг шууд `k6 run slo-test.js`, `k6 run slo-test-fail.js` гэж ажиллуулж болно. Хоёр минут болгохын тулд PowerShell дээр `$env:DURATION='2m'`, сэргэх хугацааны threshold нэмэхэд `$env:CHAOS='1'` гэж тохируулна. k6 PATH-д байхгүй бол автомат ажиллуулагчийн өмнө `$env:K6_BIN='k6.exe-ийн бүтэн зам'` гэж зааж болно.

`slo-test-fail.js` нь үндсэн скриптийг ашиглаад зөвхөн тайлангийн босгыг `p(95)<100` болгож өөрчилнө. `/report` амжилттай хүсэлт бүр дор хаяж 200 мс хүлээдэг учраас энэ босгыг зориуд зөрчинө. Харин `/cart/add`-д 50 мс тавихад localhost дээр хариу нь үүнээс хурдан тул PASS хэвээр байх боломжтой.

Threshold-ын хэлбэр болон Rate хэмжүүрийн тайлбарыг [k6 thresholds](https://grafana.com/docs/k6/latest/using-k6/thresholds/) баримтаас шалгав.

Нийт ачаалал 45.226091 хүсэлт/с байсан нь сценариод авсан ойролцоо ачаалалтай таарсан. Бусад threshold PASS хэвээр байсан тул энэ нь тайлангийн босгыг зөвхөн өөрчилсөн туршилт гэдгийг харуулна. CI дээр k6-ийн энэ тэгээс ялгаатай exit code-оор тухайн алхмыг унасан гэж үзнэ.

## Chaos туршилт

Серверийг тестийн дунд зогсоож, процесс бүрэн зогссоноос хойш 10 секунд хүлээгээд дахин асаав. Бодит зогсолт нь процесс шинээр асах болон бэлэн болсныг шалгах хугацаатайгаа нийлээд 10333 мс болсон. Зогссон, бэлэн болсон timestamp болон бүх k6 гаралт [results/chaos.txt](results/chaos.txt)-д бий.

| Хэмжилт | Утга | Үр дүн |
| --- | ---: | --- |
| Нийт хүсэлт | 5661 | 4960 амжилттай, 701 алдаатай |
| Сагсны p95 | 1.5667 мс | PASS, < 20 мс |
| Тайлангийн p95 | 397.3397 мс | PASS, < 450 мс |
| Төлбөрийн алдааны хувь | 14.8914% | FAIL, < 8% байх ёстой |
| Availability | 87.6170% | FAIL, ≥ 90% байх ёстой |
| VU-д ажиглагдсан сэргэх хугацааны p95 | 11030.0500 мс | PASS, < 12000 мс |
| Exit code | 99 | Availability болон reliability босго зөрчсөн |

Хүсэлтээр бодсон availability нь `4960 / 5661 × 100 = 87.6170%` болсон. Нийт `http_req_failed` хэвийн туршилтын 1.3709%-аас 12.3830% болж өссөн. Алдаагүй байх ёстой сагс, тайлангийн хүсэлтүүд хүртэл сервер зогссон үед `connection refused` алдаатай болсон нь [results/chaos.txt](results/chaos.txt)-ийн гаралт болон endpoint тус бүрийн check тоонд харагдана.

Цагаар тооцвол `(120000 − 10333) / 120000 × 100 = 91.3892%`, мөн 10333 мс нь 12 секундийн budget-ээс бага. Энэ нь зөвхөн төлөвлөсөн 120 секундийн цонх ба процессын зогсолтоор бодсон харьцуулалт; k6-ийн `checks` SLI биш. k6 сүүлийн эхэлсэн давталтуудаа дуусгахад цонхноос бага зэрэг илүү ажилласан нь эх гаралтад харагдана.

Хүсэлтээр тооцсон budget нь `floor(5661 × 0.10) = 566 алдаа`. Бодит 701 алдаа гарсан тул budget-ийг `701 − 566 = 135 хүсэлтээр` хэтрүүлжээ. Сервер хэвийн үед VU бүр тайлангийн 200–400 мс хүлээлт болон `sleep(1)`-ийг туулна. Харин сервер унахад гурван хүсэлт хурдан алдаа буцааж, тайлангийн хүлээлт алга болдог тул зогсолтын нэг секундэд илүү олон хүсэлт явдаг. Дээрээс нь `/pay`-ийн зориудын алдаанууд мөн budget-д орно. Тиймээс 10 секунд нь цагаар бодсон 12 секундээс бага байсан ч хүсэлтийн budget-д багтаагүй. Энэ ачаалалд 10 секундийн зогсолтыг даах хүсэлтийн 90%-ийн зорилт хэт өөдрөг байжээ; босгыг сулруулж PASS болгохын оронд зогсолтыг богиносгох шаардлагатай гэж үзлээ.

Reliability threshold мөн FAIL болсон: `/pay`-ийн 1887 хүсэлтээс 281 нь бүтэлгүйтсэн. Нэг серверийн эвдрэл availability болон reliability хоёр SLO-г зэрэг зөрчиж болохыг энэ үр дүн харуулав. Хоёр SLI-г салгахын тулд HTTP хариу ирсэн төлбөрүүдийн application алдааг `pay_application_failed` хэмжүүрээр тусад нь тоолж, хариу ирээгүй status 0 хүсэлтийг availability-д авч үзэж болно. Энэ нэмэлт хэмжүүрт 1676 хариунаас 70 нь алдаатай буюу 4.1766% байсан; үлдсэн 211 төлбөрийн алдаа нь HTTP хариу авч чадаагүй хүсэлтүүд юм.

Сэргэх хугацааны p95 нь VU тус бүрийн эхний бүтэлгүй сагсны хүсэлтээс дараагийн амжилттай сагсны хүсэлт хүртэл хэмжигдэнэ. Энэ нь процессыг дахин асаасан агшинтай яг ижил биш: VU давталт болон 1 секундийн хүлээлтээсээ хамаарч дараагийн хүсэлтээ өөр үед явуулдаг. `recovery_ms` босгыг зөвхөн `CHAOS=1` үед идэвхжүүлсэн.

## Дүгнэлт

Сценариог SLO болгоход хамгийн хэцүү нь ачаалал, хэмжих цонх, хэмжүүр гурвыг хооронд нь зөв тааруулах байлаа. Сагсанд нэмэх үйлдэл хурдан байсан тул 200 мс-ийн оронд 20 мс-ийн p95 босго сонгосон нь илүү хэрэгтэй санагдав. Төлбөрийн санамсаргүй алдаанд туршилтын хэлбэлзлийг тооцсон 8%-ийн босго хэвийн ачаалалд тохирч байлаа. Хэвийн туршилтаар бүх үндсэн threshold PASS болсон ч энэ нь сервер зогсоход хүртээмж хангалттай байна гэсэн баталгаа болоогүй. Chaos туршилт хугацаагаар бодсон error budget-ийг хүсэлтийн хувьтай шууд адилтгасан эхний тооцоог үгүйсгэлээ. Сервер унахад тайлангийн хүлээлт арилж, нэг секундэд илүү олон бүтэлгүй хүсэлт явж байгааг үр дүнгээс харж болно. Мөн серверийн нэг эвдрэл availability болон төлбөрийн reliability хоёр босгыг зэрэг зөрчсөн. Сэргэх хугацааны p95 босгодоо багтсан боловч нийт амжилттай хүсэлтийн хувь зорилтдоо хүрээгүй тул хоёр хэмжүүрийг тусад нь шалгах хэрэгтэй юм байна. Тайлангийн босгыг зориуд зөрчүүлэхэд exit code 99 гарсан нь эдгээр шаардлагыг CI дээр автоматаар шалгаж болохыг харууллаа.
